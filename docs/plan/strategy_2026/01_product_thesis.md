# DeltaQ Product Thesis

## Purpose

Зафиксировать, чем DeltaQ является как продукт и чем не является.

## Why It Matters

Сейчас у проекта много сильных подсистем, но без жёсткой продуктовой формулировки их легко воспринимать как набор крупных фич. Этот документ нужен, чтобы вся дальнейшая разработка была подчинена одной мысли.

## Current State

Проект уже сочетает:

- редактор кода;
- модульную систему;
- блочный редактор;
- UI designer;
- code generation;
- сборку и запуск;
- импорт библиотек.

Это технически богато, но продуктово создаёт риск расплывчатости.

## Target State

DeltaQ должен восприниматься как:

**среда модульной композиции программ из проверенных текстовых модулей**

а не как:

- попытка заменить все существующие IDE;
- no-code система;
- визуальный редактор "без необходимости понимать код";
- ещё один обычный редактор C/C++.

## Decisions

### Main value proposition

Пользователь ускоряет разработку, потому что:

- пишет или импортирует модуль один раз;
- проверяет его отдельно;
- повторно использует модуль как строительный блок;
- собирает более крупную систему из уже проверенных частей.

### Primary audience

Основная аудитория:

- инженерные и R&D-сценарии;
- прикладная автоматизация;
- прототипирование;
- пользователи, которым подходит модульное и графовое мышление;
- разработчики, которым важна прозрачная генерация текстового кода.

### Secondary audience

- обучение инженерному мышлению;
- небольшие open-source проекты;
- авторы библиотек и обёрток.

### Non-goals

На текущем этапе DeltaQ не должен позиционироваться как:

- универсальный конкурент CLion, VS Code, Qt Creator или Visual Studio;
- среда, скрывающая от пользователя текстовый код;
- платформа с равноправной зрелостью десятков языков;
- продукт, где polish интерфейса важнее инженерной модели.

## Implementation Directions

- Все публичные описания проекта должны ставить в центр **модуль** и **композицию модулей**.
- README, демо и документация должны объяснять DeltaQ через рабочий сценарий, а не через список фич.
- Любая новая крупная функция должна проходить фильтр:
  - усиливает ли она модуль;
  - усиливает ли она reuse;
  - усиливает ли она прозрачность.

## Acceptance Criteria

- По верхнеуровневым документам можно кратко объяснить DeltaQ одним тезисом.
- Новый участник понимает, зачем одновременно нужны код, граф и generated code.
- Внешняя презентация проекта не выглядит как перечень разнородных возможностей.

## Deferred / Not In This Phase

- Массовое позиционирование "для всех разработчиков".
- Обещания широкой поддержки многих языков как главной ценности продукта.
- Маркетинговое описание в стиле low-code/no-code.
