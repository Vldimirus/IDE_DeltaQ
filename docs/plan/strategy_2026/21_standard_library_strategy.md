# Standard Library Strategy

## Context

Если DeltaQ строится вокруг повторного использования проверенных модулей, то стандартная библиотека является не вспомогательной деталью, а центральным продуктовым активом.

## Principles

- Качество важнее количества.
- Интерфейсы важнее внутренней экзотики реализации.
- Модуль должен быть удобен в композиции.
- Библиотека должна покрывать реальные сценарии, а не демонстрационные мелочи.

## Concrete Decisions

### Library role

Стандартная библиотека должна:

- давать стартовый набор для реальной сборки программ;
- служить эталоном качества контрактов;
- показывать стиль проектирования модулей в DeltaQ.

### Required v1 categories

Для `v1` фиксируется следующий обязательный набор категорий:

- `control`
- `io`
- `string`
- `conversion`
- `logic`
- `math`
- `desktop`

Этот список должен использоваться одинаково:

- в стратегии;
- в audit стандартной библиотеки;
- в сортировке core-категорий внутри IDE;
- в дальнейшей чистке и расширении библиотеки.

### Audit baseline

`Phase 2` начинается не с добавления новых десятков модулей, а с выравнивания уже существующей библиотеки.

Для этого у standard library должен быть один источник истины:

- checked-in `.dqmod` в `modules/core`.

`StandardLibrary` в коде должен отвечать за:

- audit;
- ordering;
- curation;
- копирование/синхронизацию pack-а;

но не за второе, независимое определение тех же модулей в hardcoded C++.

Базовый audit `v1` должен проверять:

- наличие обязательных категорий;
- наличие ключевых модулей для главного workflow;
- единый snake_case naming;
- согласованность `module.id` со схемой `core.<category>.<name>`;
- отсутствие дублирующих id и конфликтующих имён внутри категории;
- совпадение контрактов у ключевых модулей с ожидаемыми `v1`-сигнатурами.

Только после прохождения этого audit имеет смысл расширять библиотеку новыми модулями.

### Display curation

Стандартная библиотека должна быть согласована не только на уровне файлов и контрактов, но и на уровне того, как она читается пользователем внутри IDE.

Для `v1` это означает:

- один и тот же порядок core-категорий в `Module Manager` и `Module Palette`;
- ключевые модули внутри категории должны идти раньше второстепенного алфавитного хвоста;
- библиотека должна выглядеть как curated system, а не как случайный список файлов.

### Module roles

Для `v1` core-модули должны иметь явную product-curation роль:

- `essential`
- `convenience`
- `specialized`
- `legacy` — только если модуль реально устарел и имеет более правильную альтернативу

Эта роль должна использоваться одновременно:

- в display-порядке библиотеки;
- в tooltip и discoverability внутри IDE;
- при принятии решений, что считается опорным baseline, а что является лишь удобным дополнением;
- при дальнейшей чистке слабых или спорных модулей.

Первая практическая форма такой чистки — не мгновенное удаление, а перевод
слабого shortcut-модуля в `legacy`, если у него уже есть более ясная
композиционная альтернатива.

Для checked-in `core` pack этого уже недостаточно на уровне идей: каждая
единица библиотеки должна иметь explicit review-решение по роли, иначе audit
считается незавершённым.

### Quality bar for a module

Хороший модуль:

- имеет понятное имя и назначение;
- имеет чистый и ясный контракт;
- не содержит неожиданных побочных эффектов;
- проходит минимальную проверку;
- хорошо читается в графе;
- помогает собирать более крупные сценарии.

### Documentation standard

Для каждого значимого модуля должны быть понятны:

- назначение;
- входы и выходы;
- типы;
- ограничения;
- expected behavior;
- место в примерах.

Текущий `v1`-формат документации модуля:

- `description` — краткое назначение;
- `deltaq.doc.when_to_use` — когда использовать;
- `deltaq.doc.limitations` — ограничения и caveats.

Этот формат должен быть виден пользователю прямо внутри IDE:

- в `Module Manager`;
- в tooltip `Module Palette`;
- в tooltip дерева модулей.

Для checked-in `core` pack этот стандарт должен применяться целиком, а не только
к showcase-модулям или imported pack-ам.

## Success Criteria

- Библиотека помогает собрать 2-3 эталонных проекта без ощущения, что половину приходится обходить вручную.
- Модули воспринимаются как надёжные кирпичи системы.
- Библиотека поддерживает продуктовую идею DeltaQ, а не просто увеличивает счётчик фич.
