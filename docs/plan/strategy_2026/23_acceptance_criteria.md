# Acceptance Criteria

## Context

Проекту нужны не только технические тесты, но и стратегические критерии готовности фаз. Иначе легко объявлять большой прогресс при недостаточно зрелом пользовательском результате.

## Principles

- Критерии должны быть измеримыми или хотя бы однозначно проверяемыми.
- Фаза считается завершённой не по объёму работы, а по полезному результату.
- Acceptance должен учитывать и инженерную, и продуктовую сторону DeltaQ.

## Concrete Decisions

### Phase 1 acceptance

- Главный workflow проходит end-to-end без скрытых ручных шагов.
- Пользователь понимает роль `.dqmod`, `.dqgraph`, `.dqui` и generated files.
- Generated code можно быстро сопоставить с источником.
- Ошибки build/codegen локализуются в понятных местах.
- Один эталонный проект собирается и запускается стабильно.

### Phase 2 acceptance

- Стандартная библиотека позволяет собрать несколько meaningful сценариев.
- Для ключевых модулей понятен контракт и статус проверки.
- Reuse модулей ощущается как практическое преимущество, а не теоретическая возможность.

### Phase 3 acceptance

- Новый пользователь понимает идею продукта по README и примерам.
- Есть 2-3 сильных demo-потока.
- Проект можно показать как целостный open-source инструмент с ясной идентичностью.

### Ongoing review questions

На каждом цикле нужно задавать:

1. Стал ли сильнее главный workflow?
2. Стала ли яснее модель модуля?
3. Стал ли generated code прозрачнее?
4. Стала ли стандартная библиотека полезнее?
5. Стало ли легче объяснить DeltaQ новому человеку?

## Success Criteria

- Фазы оцениваются по реальному состоянию продукта, а не по числу реализованных подсистем.
- Документы можно использовать как критерий остановки и приоритизации.
- Появляется единый способ говорить о готовности DeltaQ.
