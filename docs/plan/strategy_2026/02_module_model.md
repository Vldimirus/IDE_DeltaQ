# DeltaQ Module Model

## Purpose

Определить модуль как главный объект DeltaQ и убрать двусмысленность между кодом, графом и метаданными.

## Why It Matters

Если модель модуля нестрогая, то граф, codegen, стандартная библиотека, импорт библиотек и мультиязычность не имеют надёжной общей основы.

## Current State

В проекте уже существуют:

- атомарные модули в `.dqmod`;
- составные модули на основе графов;
- UI-ориентированные модули;
- generated code и runtime-модули;
- направление на мультиязычность.

Это создаёт основу, но требует одного строгого определения.

## Target State

Модуль в DeltaQ определяется как:

**контрактно описанная операция с явными входами, выходами, типами, семантикой выполнения и проверяемой реализацией**

## Decisions

### Source of truth

Для атомарного модуля:

- контракт и metadata описываются в `.dqmod`;
- исполняемая реализация задаётся текстовым `sourceCode` и связанными include/dependency-данными.

Для составного модуля:

- контракт модуля выводится из его внешнего интерфейса;
- реализация задаётся внутренним `.dqgraph`.

### Mandatory module properties

Каждый модуль должен иметь:

- устойчивый `id`;
- имя и краткое назначение;
- категорию;
- язык реализации;
- явные input/output порты;
- типы портов;
- режим выполнения: `data`, `execution`, либо комбинированный;
- исходную реализацию или ссылку на графовую реализацию;
- информацию, достаточную для codegen и повторного использования.

### Contract over implementation

Контракт модуля первичен по отношению к способу отображения в IDE.

Это означает:

- графическая нода — только визуальное представление модуля;
- язык реализации модуля вторичен, пока соблюдается контракт;
- UI-модуль не должен иметь отдельную "магическую" модель, не согласованную с общим понятием модуля.

### Verified module

Модуль считается проверенным, если:

- его контракт валиден;
- его реализация проходит минимальный compile/test pipeline;
- его поведение достаточно предсказуемо для повторного использования.

### Atomic vs composite

Атомарный модуль:

- реализован как текстовая функция, процедура или inline-runtime fragment;
- проверяется на уровне собственного кода и контрактов.

Составной модуль:

- реализован как граф других модулей;
- проверяется через compile/test конечного графа и согласованность внешнего интерфейса.

## Implementation Directions

- Все решения по UI, graph editor и codegen должны ссылаться на эту модель.
- Для мультиязычности развивать не "поддержку языка вообще", а **совместимость модуля по контракту**.
- Внутренние документы и код должны различать:
  - контракт модуля;
  - реализацию модуля;
  - визуальное представление модуля;
  - артефакты генерации модуля.

## Acceptance Criteria

- Можно однозначно объяснить различие атомарного и составного модуля.
- Нет противоречий между тем, как модуль хранится, отображается и собирается.
- Понятно, что нужно для проверки нового модуля.
- Появляется база для дальнейшей мультиязычной стратегии.

## Deferred / Not In This Phase

- Полная формализация ABI/FFI между многими языками.
- Сложная пакетная и сетевая экосистема модулей.
- Расширенные политики версионирования beyond minimal contract compatibility.
