# DeltaQ Strategy 2026

## Purpose

Этот документ является главным входом в стратегию развития DeltaQ на ближайшие `6-12 месяцев`.

DeltaQ развивается не как универсальная IDE общего назначения, а как **open-source среда модульной композиции ПО**, где:

- модуль является основной единицей инженерной работы;
- граф является способом композиции модулей;
- текстовый код остаётся проверяемым и прозрачным источником результата;
- IDE помогает собирать систему из уже проверенных блоков.

## Why It Matters

Без единой стратегии проект легко расползается в набор крупных, но слабо связанных подсистем: редактор, граф, UI designer, импорт библиотек, codegen, мультиязычность.

Этот набор планов нужен для того, чтобы:

- зафиксировать продуктовую идентичность DeltaQ;
- сфокусировать разработку на одном сильном сценарии;
- ограничить scope и отложить второстепенные направления;
- сделать дальнейшую реализацию и ревью решений последовательными.

## Product Thesis

DeltaQ — это среда, в которой программа собирается из **проверенных текстовых модулей с явными контрактами**. Пользователь может:

1. написать или импортировать модуль;
2. проверить его отдельно;
3. соединить модули в граф;
4. получить прозрачный текстовый результат;
5. собрать и запустить программу.

Главная ценность DeltaQ не в том, что пользователь "рисует вместо программирования", а в том, что он **ускоряет разработку за счёт повторного использования надёжных модулей**.

## Strategic Horizon

Горизонт: `6-12 месяцев`.

Главный результат ближайшего цикла: довести до зрелости **core workflow**:

`модуль -> граф -> код -> сборка -> запуск`

Успешный результат цикла:

- модель модуля описана без противоречий;
- основной workflow стабилен и предсказуем;
- generated code прозрачен для пользователя;
- стандартная библиотека даёт реальное ускорение разработки;
- проект можно убедительно показать внешнему пользователю через 2-3 сильных примера.

## Strategic Phases

### Phase 1: Core Stabilization

Фокус:

- строгая модель модуля;
- прозрачный codegen/build pipeline;
- устранение конфликтов между `.dqmod`, `.dqgraph`, `.dqui`;
- один надёжный сквозной сценарий.

Критерий выхода:

- пользователь может пройти основной путь без концептуальной путаницы;
- сгенерированный код и артефакты сборки предсказуемы;
- базовая стандартная библиотека реально пригодна для сборки маленького приложения.

### Phase 2: Module Ecosystem

Фокус:

- качество стандартной библиотеки;
- тестирование модулей;
- документация контрактов;
- примеры повторного использования;
- import/wrapping как ускоритель пополнения библиотеки.

Критерий выхода:

- библиотека модулей выглядит как системная ценность проекта, а не приложение к редактору.

### Phase 3: Showcase And Adoption

Фокус:

- demo-проекты;
- onboarding;
- README и документация верхнего уровня;
- polished демонстрация главного сценария.

Критерий выхода:

- внешний пользователь понимает идею и может повторить базовый сценарий за короткое время.

## Ordering Rules

Приоритет решений:

1. Модель модуля и контрактов.
2. Сквозной core workflow.
3. Прозрачность генерации и сборки.
4. Качество стандартной библиотеки.
5. Примеры и внешняя подача.

То, что не помогает этим пунктам, не должно становиться главным направлением разработки.

## Governance

Все новые стратегические решения должны сверяться с этим документом.

Если новая идея:

- не усиливает модель модуля;
- не делает сильнее основной workflow;
- не повышает прозрачность или практическую ценность библиотек;

то она считается второстепенной и должна быть отложена.
