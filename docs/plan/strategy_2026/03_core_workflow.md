# DeltaQ Core Workflow

## Purpose

Зафиксировать главный пользовательский сценарий, вокруг которого должен оптимизироваться весь проект.

## Why It Matters

Без одного сильного workflow проект легко превращается в набор отдельных редакторов и сервисов. DeltaQ должен выигрывать не количеством фич, а качеством одного сквозного пути.

## Current State

Сейчас в проекте уже есть основные элементы workflow:

- создание и редактирование модулей;
- визуальная сборка графов;
- pre-build генерация исходников;
- сборка и запуск проекта;
- UI layout и desktop runtime.

Но эти элементы нужно рассматривать как единый сценарий, а не как параллельные подсистемы.

## Target State

Главный workflow DeltaQ:

1. Пользователь создаёт или импортирует модуль.
2. Пользователь понимает контракт модуля.
3. Пользователь отдельно проверяет модуль.
4. Пользователь использует модуль в графе.
5. Пользователь получает прозрачный generated code.
6. Пользователь собирает и запускает проект.
7. Пользователь может связать результат обратно с модулями и графом.

## Decisions

### Workflow priority

Все крупные решения должны проверяться вопросом:

**делает ли это лучше основной workflow?**

Если нет, направление не является приоритетом.

### User expectations at each stage

#### Module authoring

Пользователь должен видеть:

- имя и назначение модуля;
- входы и выходы;
- текст реализации;
- статус проверки.

#### Graph composition

Пользователь должен видеть:

- какие модули доступны;
- как их соединять;
- где начинается и заканчивается execution flow;
- как выглядит контракт составного модуля.

#### Code generation

Пользователь должен понимать:

- какие файлы сгенерированы;
- какой модуль или граф их породил;
- где generated code, а где пользовательский код;
- какие include и runtime-фрагменты добавлены.

#### Build and run

Пользователь должен получать:

- предсказуемый pipeline;
- понятную диагностику;
- отсутствие скрытой пересборочной магии;
- воспроизводимый результат.

## Implementation Directions

- Внутренние улучшения UI оценивать через этот workflow, а не локально.
- В будущем демо, обучающие материалы и примеры строить вокруг этого пути.
- Любые новые сущности в проекте должны либо усиливать workflow, либо быть отложены.

## Acceptance Criteria

- Можно пройти путь от создания модуля до запуска результата без концептуальных разрывов.
- Пользователь понимает, почему проект содержит `.dqmod`, `.dqgraph`, `.dqui` и generated sources.
- Generated code читаем и связан с источником происхождения.
- Основной workflow достаточно стабилен для демонстрации внешним пользователям.

## Deferred / Not In This Phase

- Сложные альтернативные пользовательские сценарии.
- Одновременная оптимизация всех подсистем вне главного пути.
