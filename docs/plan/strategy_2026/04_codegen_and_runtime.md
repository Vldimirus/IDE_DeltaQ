# DeltaQ Codegen And Runtime Strategy

## Purpose

Зафиксировать стратегию генерации кода и runtime-поведения так, чтобы она усиливала доверие к DeltaQ, а не превращала проект в непрозрачную надстройку.

## Why It Matters

Для DeltaQ generated code не является побочным эффектом. Это один из главных носителей доверия. Если пользователь не понимает, что было сгенерировано и почему, модель модульной композиции начинает восприниматься как магия.

## Current State

В проекте уже есть:

- графовая компиляция в C-код;
- pre-build генерация файлов;
- runtime-модули для desktop/SDL;
- generated UI sources;
- сборка через CMake pipeline.

## Target State

Генерация и runtime должны работать по следующим правилам:

- generated code всегда объясним по происхождению;
- модульный граф не скрывает бизнес-логику вне графа;
- runtime-модули оформлены как обычные модули там, где это возможно;
- сборка воспроизводима и предсказуема.

## Decisions

### Transparency first

Пользователь должен иметь возможность быстро понять:

- какой файл сгенерирован;
- из какого графа, модуля или layout он получен;
- где код пользователя, а где кодогенерация;
- какие runtime-зависимости добавлены автоматически.

### Graph is composition, not hidden runtime

Логика главного сценария должна быть выражена модулями и графом, а не спрятанными шаблонами и особыми исключениями.

### Minimal hidden behavior

Скрытая логика допускается только там, где без неё невозможно обеспечить базовую работоспособность платформы, но даже в таких случаях она должна быть явно документирована и отслеживаема.

### Multilanguage strategy

На горизонте `6-12 месяцев` мультиязычность рассматривается как архитектурная рамка, а не как требование одинаково довести несколько языковых backend-ов.

Ближайший practical path:

- один основной зрелый backend;
- абстракции не ломают расширение на будущие языки;
- новые языки не отнимают приоритет у основного workflow.

## Implementation Directions

- Документировать происхождение generated sources и правила их жизненного цикла.
- Стараться переносить особую runtime-логику в явные модули и документы, а не держать её как скрытое знание.
- Укреплять build pipeline вокруг воспроизводимости, а не количества supported modes.

## Acceptance Criteria

- Пользователь может объяснить структуру generated project.
- Не возникает ощущения, что критически важные строки программы появились "сами по себе".
- Ошибки генерации и сборки локализуются в понятные места pipeline.

## Deferred / Not In This Phase

- Многобэкендная реализация production-grade качества для нескольких языков.
- Сложный отдельный runtime для каждой новой подсистемы без строгой необходимости.
